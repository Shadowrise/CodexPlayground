# Руководство для AI-агентов: проект Kirby

Этот файл читает любой AI-агент перед работой с репозиторием. Здесь — что это за
проект, как его запускать и проверять, и правила, которые не дают вернуться
проблемам с производительностью. История изменений по задачам лежит в
[PROJECT_MEMORY.md](PROJECT_MEMORY.md): каждая завершённая задача добавляет туда
запись в конец файла.

## Что это за проект

Браузерная 3D-игра с общей поляной и мультиплеером.

- `kirby-game/` — клиент: Three.js 0.180, Vite 7, TypeScript. Точка входа —
  `src/main.ts` (сборка сцены и главный цикл). Отдельная локация — арена
  Метакнайта (`src/meta-knight-*.ts`), она подгружается при входе в портал.
- `game-server/` — Cloudflare Worker с двумя Durable Objects: общая комната до
  14 игроков и архив визитов. Клиенты сами симулируют мир, один из них — хост.
- `kirby-game/public/` — модели, музыка и запечённый мир `world/environment.*`.
- `kirby-game/artifacts/`, `kirby-game/design/` — отчёты прошлых исследований
  и исходники ассетов. Для запуска игры не нужны.

## Команды

Все команды выполняются в `kirby-game/`.

| Задача | Команда |
|---|---|
| Запуск клиента | `npm run dev` (порт 5173) |
| Проверка типов | `npx tsc --noEmit` |
| Все тесты | `npm test` (1202 теста, около 2–3 минут) |
| Один файл тестов | `npx tsx --test tests/<имя>.test.ts` |
| Production-сборка | `npm run build` |
| Сервер | `npm run dev` в `game-server/` (порт 8787) |

Перед тем как сказать «готово»: `npx tsc --noEmit`, `npm test`, а для правок
отрисовки — ещё проверка в настоящем браузере (см. «Как измерять»).

## Правила работы с репозиторием

- **Окончания строк — CRLF** во всех исходниках, тестах и документах. Новый
  файл нужно привести к CRLF.
- **Стиль кода плотный**: длинные строки, несколько выражений в строке.
  Комментарии в коде — на английском и объясняют «почему». Документы — на русском.
- **Не коммитьте случайно перезапечённый мир.** Dev-сервер пересобирает
  `public/world/environment.bin.gz` и `environment.manifest.json`, когда меняются
  исходники окружения. Хеш запекания зависит от платформы. Включайте эти файлы
  в коммит, только если менялось само окружение.
- **Дробные степени дают разный последний бит на разных движках.** Высота горы
  считается через `**1.35`; тесты, которые сверяют такие числа, округляют их
  (пример — `tests/mountain-woodland.test.ts`).
- **Сетевой протокол общий для клиента и сервера** (`src/network-protocol.ts`).
  Клиент и сервер выкладываются вместе.
- **После задачи добавьте запись в конец `PROJECT_MEMORY.md`**: заголовок
  `## Название — ГГГГ-ММ-ДД, локально` (или «выпуск»), затем что сделано,
  почему, как проверено и был ли commit/push.

## Производительность: откуда брались проблемы

В ноябре 2026 года игра давала 45–49 FPS на RTX 3050 при простаивающей
видеокарте, а первый вход на арену занимал 25–31 секунду. Причин было пять, и
ни одна не была связана с числом треугольников.

1. **Упор в процессор внутри `renderer.render()`.** Видеокарта тратила 7–9 мс
   на кадр, процессор — 16–18 мс: обход сцены, пересчёт матриц и накладные
   расходы на каждый вызов отрисовки.
2. **Работа над тем, чего не видно.** Каждый кадр пересчитывались матрицы
   4000 узлов скрытых моделей светлячков и скрытых NPC.
3. **Пересборка шейдерных параметров каждый кадр** — 100–160 раз. Её вызывали
   прозрачные двусторонние материалы и материалы, общие для мешей разного вида.
4. **Шейдеры, которые Direct3D компилирует секундами.** Шейдер планет с
   процедурным шумом в циклах компилировался 3–12 секунд на вариант.
5. **Синхронная работа за экраном загрузки.** Съёмка карты отражений
   замораживала страницу на 4–7 секунд.

Отдельно: на ноутбуках с двумя видеокартами Chrome по умолчанию берёт
встроенную. На Intel UHD игра даёт 11–15 FPS и упирается уже в видеокарту.
`powerPreference:'high-performance'` на это не влияет; проверяется в
`chrome://gpu`, исправляется в параметрах графики Windows.

## Правила отрисовки (кадр)

### Скрытое не должно стоить ничего

- Мировые матрицы обновляет `StaticWorldMatrices` (`src/static-world.ts`), а не
  Three. Статичный корень регистрируется через `worldMatrices.add(root)` и
  больше не обходится. Скрытый динамический корень пропускается целиком.
  Корень, у которого скрытые ветки нужны только для рисования, регистрируется
  через `worldMatrices.skipHidden(root)`.
- **Следствие: у скрытого узла матрица может быть устаревшей.** Код, который
  читает `matrixWorld` или вызывает `localToWorld`/`worldToLocal` у кости
  персонажа или детали аттракциона, обязан сначала вызвать
  `node.updateWorldMatrix(true,false)`. `getWorldPosition()` делает это сам.
- Анимация, которую никто не видит, не должна идти с полной частотой.
  Декоративные позы идут через `CosmeticClock` (`src/cosmetic-clock.ts`):
  30 Гц дальше 65 м, 10 Гц дальше 120 м.
- Дальние персонажи рисуются упрощённой геометрией: `updateVisibility(root,
  camera, exists, false, ACTOR_DISTANCE, true)` в главном цикле. Новый тип
  персонажа должен вызвать `prepareCharacterDetail(template)` при загрузке,
  иначе первое упрощение даст подвисание.

### Материалы

- **Прозрачный материал с `side:DoubleSide` обязан иметь
  `forceSinglePass:true`**, если геометрия плоская или тонкая (тени-накладки,
  пена, таблички, крылья). Иначе Three рисует его дважды и дважды за кадр
  сбрасывает программу.
- **Один материал — один вид меша.** Нельзя делить материал между скелетным и
  жёстким мешем, между `InstancedMesh` и обычным, между мешем с морфами и без.
  Для второго вида делается копия (`material.clone()`). Полный признак вида —
  `meshKind()` в `src/pigeon-appearance.ts`: скелет, число морфов, морфы
  нормалей и цветов, альфа в цвете вершин, касательные.
- **Не ставьте `material.needsUpdate=true` каждый кадр.** Смена цвета,
  прозрачности и uniform-значений этого не требует.
- **Одинаковые поверхности — один экземпляр материала.** Не создавайте материал
  на каждый меш, ячейку или персонажа, если он не меняется индивидуально. Для
  запечённого окружения это делает `shareIdenticalMaterials`
  (`src/shared-materials.ts`), для лиц NPC — кеш в `src/variants.ts`.
- **Число источников света в сцене должно быть постоянным.** Смена числа
  источников меняет программы всех освещаемых материалов. На арене пять
  точечных источников существуют всегда, выключенные имеют нулевую яркость.

### Вызовы отрисовки

Каждый вызов стоит процессору порядка 10–25 мкс, поэтому 150 мелких мешей
дороже одного большого. Перед добавлением объекта из многих частей выберите
способ объединения:

| Случай | Средство |
|---|---|
| Неподвижные соседние детали с одинаковым материалом | `batchRigidMeshes(parent)` из `src/rigid-batch.ts` |
| Много копий одной геометрии | `InstancedMesh`; для прозрачных — сортировка по глубине, как в `SkyGlassBodies` |
| Части, которые почти всегда в покое, но иногда двигаются | `RestBatch` из `src/rest-batch.ts` |
| Декорации окружения по ячейкам | `SceneryInstanceBatch` из `src/scenery-batch.ts` |
| Дальний вид сложного объекта | один снимок-меш, как `CoasterDetail` |

Меш, который должен остаться видимым для логики и лучей, но не рисоваться,
получает материал с `visible=false`. `mesh.visible=false` и смена слоя ломают
лучи и проверки в тестах.

Не создавайте объекты в цикле кадра (`new Vector3()` внутри `update`) —
переиспользуйте заранее созданные.

## Правила загрузки (шейдеры и ресурсы)

- **Шум в шейдере берётся из текстуры, а не считается в цикле.** Процедурные
  `hash`/`noise`/`fbm` с циклами Direct3D разворачивает и компилирует
  секундами. Готовая решётка — `planetNoiseTexture()` в
  `src/meta-knight-cosmic-sky.ts`. Специализация шейдера через константы не
  помогает: дорог сам шум.
- **Каждую новую шейдерную программу нужно измерить** скриптом
  `scripts/perf/arena-shader-compile.js`. Норма — до 0,3 с, всё дольше 1 с —
  дефект.
- **Ничего не рисуйте несобранной программой.** Перед показом сцены —
  `await renderer.compileAsync(scene,camera)`. Проход в текстуру (карта
  отражений, PMREM) использует другие варианты программ; их нужно собрать
  заранее при том же состоянии рендерера, как в `prepareEnvironment`
  (`src/meta-knight-arena.ts`).
- **То, что понадобится не сразу, собирается в фоне.** `renderer.compile()`
  запускает сборку, готовность проверяется через `program.isReady()`, а до
  готовности объект не показывается или рисуется упрощённым материалом
  (`planetStandIn`). Образец — `prepare()` и `warmLate()` в
  `src/meta-knight-battle-view.ts`. Показ объекта с неготовой программой
  замораживает страницу до конца сборки.
- **Процедурные текстуры, геометрия и звуки строятся один раз за сессию** и
  хранятся в кеше на уровне модуля. `dispose()` освобождает только копию на
  видеокарте; повторно использованный объект загрузится снова.
- **Тяжёлая генерация пишется как генератор с шагами** и выполняется
  порциями по несколько миллисекунд (`arenaAssetWork` в
  `src/meta-knight-arena-warm.ts`, запуск — `prewarm()` в
  `src/meta-knight-arena-travel.ts`).
- В production-сборке `renderer.debug.checkShaderErrors` выключен. Ошибки
  шейдеров видны только в dev-режиме.

## Как измерять

Замеры делаются в настоящем браузере. Запустите dev-сервер на порту 5184
(`npm run dev -- --port 5184 --strictPort`) и выполните в `kirby-game/`:

| Что проверить | Команда |
|---|---|
| Время кадра, вызовы по группам сцены, число материалов | `node scripts/perf-harness.mjs scripts/perf/meadow-frame.js` |
| Пересборки программ каждый кадр и их причина | `node scripts/perf-harness.mjs scripts/perf/meadow-programs.js --three` |
| Пересборки программ у диких голубей вблизи | `node scripts/perf-harness.mjs scripts/perf/meadow-pigeons.js --three` |
| Семейства одинаковых материалов | `node scripts/perf-harness.mjs scripts/perf/meadow-materials.js` |
| Время входа на арену | `node scripts/perf-harness.mjs scripts/perf/arena-load.js` |
| Время компиляции каждого шейдера арены | `node scripts/perf-harness.mjs scripts/perf/arena-shader-compile.js` |
| Кадры в бою по всем фазам | `node scripts/perf-harness.mjs scripts/perf/arena-duel.js` |
| Подёргивания на поляне при фоновой подготовке арены | `node scripts/perf-harness.mjs scripts/perf/arena-prewarm.js` |

Описание помощников для собственных сценариев — в шапке
`scripts/perf-harness.mjs`.

Правила замера:

- **Сначала измерьте, потом правьте.** Разделите время кадра на обновление,
  отрисовку на процессоре и время видеокарты. Уменьшение числа треугольников
  не помогает, когда упор в процессор.
- **Сравнивайте варианты в одном запуске, чередуя их.** Абсолютные числа
  разных запусков расходятся на 20–30% из-за частоты процессора и времени
  суток в игре.
- **Headless Chrome сам берёт встроенную видеокарту.** Скрипт передаёт
  `--force_high_performance_gpu`; модель видеокарты проверяйте в выводе.
- FPS упирается в частоту монитора (здесь 74–75 Гц). Смотрите на миллисекунды.
- Числа dev-сборки. В production не замерялось.

## Ориентиры после оптимизации

RTX 3050 Laptop, окно 1920×1080, масштаб 125%, дальность 750 м, одиночная игра.

| Показатель | Значение | Было до оптимизации |
|---|---|---|
| Поляна, взгляд через всю карту: `render()` | 10–12 мс | 16–18 мс |
| Поляна: вызовов отрисовки за кадр | 700–850 | 900–1050 |
| Поляна: материалов / программ | 770 / около 120 | 1046 / около 130 |
| Поляна: пересборок программ за кадр | 0 | 100–160 |
| Пересчёт мировых матриц | 0,25 мс | 3,2 мс |
| Арена: `render()` / вызовов | 3 мс / 160–200 | не менялось |
| Первый вход на арену после фоновой подготовки | 1,1–1,4 с | 25–31 с |
| Первый вход без подготовки | 3,2 с | 25–31 с |
| Повторный вход на арену | 0,5–0,6 с | 1,4 с |

Если после правки показатель ушёл от ориентира заметно дальше разброса,
найдите причину до завершения задачи.

## Чек-лист для правки, которая добавляет объекты или эффекты

1. Сколько вызовов отрисовки добавилось? Проверьте `meadow-frame.js`.
2. Есть ли прозрачные двусторонние материалы без `forceSinglePass`?
3. Не делится ли материал между мешами разного вида? `meadow-programs.js
   --three` должен показывать ноль пересборок за кадр.
4. Обновляется ли что-то, когда объект скрыт или далеко?
5. Читает ли новый код матрицы узлов, которые могут быть скрыты?
6. Новый шейдер: сколько он компилируется? Есть ли в нём шум в цикле?
7. Новая процедурная текстура или геометрия: закеширована ли она и не строится
   ли синхронно во время игры?
8. `npx tsc --noEmit`, `npm test`, проверка картинки в браузере.

## Что известно, но не сделано

- Лодки (около 66 вызовов), дальние тележки горок (11 вызовов), тени деревьев
  и светлячки ближе 28 м (около 30 вызовов на каждого) не объединены.
- На слабых видеокартах нет автонастройки качества: по умолчанию 125%,
  сглаживание 4× и дальность 750 м.
- Пока игрок на арене, поляна симулируется с полной частотой (около 2 мс на
  кадр). В сети хост обязан считать NPC, поэтому частоту целиком снижать нельзя;
  можно пропускать только косметику в одиночной игре.
- Автозапуск фоновой подготовки арены от настоящего открытия портала, арена
  Мета Пиджи и сетевая дуэль после оптимизаций в браузере не проверялись.
- На встроенной графике Intel, на телефоне и в production-сборке замеров нет.
